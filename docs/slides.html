The problemHow results are handled today

  • Scores typed into personal Excel files, emailed and merged by hand
  • Totals, grades and GPAs calculated manually, so errors happen
  • Anyone with the file can change a grade, and nothing records it
  • Results take weeks to be released
  • Notice boards expose every student's grades

Goal

One secure system where lecturers enter scores once, grades are computed automatically, the exams office approves them, and each student privately sees only their own published results.

Objectives & scope

Objectives

  • Manage students, lecturers, courses and enrolment
  • Validated score entry (CA /40, exam /60)
  • Automatic grade, GPA, CGPA and class of degree
  • Approval workflow before release
  • Private student access and a full audit trail

Stakeholders

  • Exams officer (admin): approves and publishes
  • Lecturers: enter and submit scores
  • Students: view results and CGPA
  • Head of Department, IT unit, parents

Out of scope

Fees, SMS alerts, Excel import, signed PDF transcripts

Requirements15 functional · 10 non-functional · 7 business rules (IEEE 830 SRS)

Key functional requirements

  • FR-08 Enter CA + exam, system computes grade
  • FR-10 Submit only when every student is scored
  • FR-11 Admin publishes or returns results
  • FR-12 Students see only published results
  • FR-13 CGPA and class of degree

Key non-functional requirements

  • bcrypt passwords; protection against SQL injection, XSS and CSRF
  • Role check on every page
  • Database integrity: foreign keys, unique keys, CHECK constraints
  • Works on phones; runs on XAMPP or shared hosting

Design patterns

  • MVC: separates logic, data and HTML
  • Front Controller: one entry point, one access check
  • Repository: all SQL in one place
  • Singleton: one database connection
  • Strategy: grading scale can be swapped without code changes
