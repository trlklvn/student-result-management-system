Executive Summary

This report documents the complete development of a Student Result Management System (SRMS): a web application that lets a department record continuous assessment and examination scores, compute grades and grade point averages automatically, approve results before release, and publish them securely to students.

The project followed an Agile Scrum process adapted for a single developer, run as four one-week sprints. Requirements were captured as 15 functional and 10 non-functional requirements and formalised in an IEEE 830-style SRS. The system was modelled with use case, class, sequence, state and activity diagrams, and built with PHP 8 and MySQL 8 on a layered Model–View–Controller architecture using the Front Controller, Repository, Singleton and Strategy design patterns.

A working prototype is delivered with source code under Git version control. Testing combined 8 unit, 9 integration and 9 system tests: all 26 pass. Exploratory testing found 3 defects; each was fixed, given a regression test and recorded in the defect report.

1. Project Proposal

1.1 Background

In many Ghanaian tertiary institutions, examination results are still processed with spreadsheets passed between lecturers, heads of department and the examinations office. Lecturers type scores into personal Excel files, which are emailed or copied onto flash drives, merged by hand, checked, and finally printed and pinned on notice boards or uploaded as PDFs. Each hand-over is a chance for errors, delays and unauthorised changes.

1.2 Problem Statement

The current manual process for managing student results has five main problems:

  1. Calculation errors: totals, letter grades and GPAs are computed by hand or with copied spreadsheet formulas, so mistakes are common and hard to spot.
  2. No control over changes: once a spreadsheet leaves the lecturer, anyone can edit it, and nothing records who changed what.
  3. Slow release: students wait weeks for results to be collated, approved and posted.
  4. Privacy: results on public notice boards expose every student's grades to everyone.
  5. No single source of truth: transcripts must be rebuilt from many separate files.

The department needs a central system in which lecturers enter scores once, grades are computed consistently, the examinations officer approves results before release, and each student privately sees only their own published results.

1.3 Objectives

General objective: to design and develop a secure web-based system that manages student examination results from score entry to publication.

Specific objectives:

  1. Let administrators register students, lecturers and courses, and enrol students in courses.
  2. Let lecturers enter CA and exam scores only for courses assigned to them, with validation of score ranges.
  3. Compute totals, letter grades, grade points, semester GPA, CGPA and class of degree automatically and consistently.
  4. Enforce an approval workflow (draft → submitted → published) so that no result reaches students without approval.
  5. Let each student securely view only their own published results.
  6. Keep an audit trail of every important action.
  7. Verify correctness through automated unit, integration and system testing.

2. Software Process Model

2.1 Models Considered

2.2 Selected Model: Agile Scrum, adapted for a solo developer

The project used Scrum with four one-week sprints. Because there is one developer, the Scrum roles were adapted:

  • Product Owner: the project supervisor and the examinations office, represented by the developer through interviews and document analysis.
  • Scrum Master and Development Team: the developer.
  • Artefacts: a product backlog of user stories, a sprint backlog for each sprint (Section 8.3), and a working increment at the end of each sprint.
  • Events: sprint planning at the start of each week, a short daily self-review, a sprint review demo to the supervisor, and a retrospective note.

2.3 Justification

  1. Early working software: login and admin features worked at the end of Sprint 2, so the supervisor could give feedback on real screens instead of documents only.
  2. Changing requirements: grading scales and approval rules differ between institutions. Agile let these details change between sprints; the Strategy pattern (Section 5.2) keeps the grading scale replaceable.
  3. Testing throughout: automated tests were written in the same sprint as the code, which caught defects early (Section 7.6).
  4. Fixed deadline, flexible scope: with a fixed submission date, Scrum's priority-ordered backlog makes sure the most valuable features (score entry, grading, publication) are done first, while low-priority items (bulk import, notifications) move to future work.
  5. Documentation still produced: each sprint's definition of done included the matching documents, which gives the documentation benefits of Waterfall without its rigidity.

3.4 Software Requirements Specification (SRS)

The SRS follows the structure of IEEE Std 830-1998.

3.4.1 Introduction

Purpose: this SRS defines the requirements of the Student Result Management System, version 1.0, for the developer, the supervisor and the examinations office.
Scope: SRMS manages examination results from score entry through approval to publication, as described in Section 1.4.
Definitions: CA – continuous assessment (out of 40); Exam – final examination (out of 60); GPA – grade point average for one semester; CGPA – cumulative GPA across all semesters; Enrolment – the registration of a student in a course; Publish – release approved results to students.

3.4.2 Overall Description

Product perspective: a stand-alone web application with a browser client, a PHP application server and a MySQL database (Section 5.1).
Product functions: user and course administration, enrolment, score entry and grading, approval workflow, result publication, transcript and GPA computation, auditing.

Operating environment: Apache or any PHP 8.1+ web server, MySQL 8, modern browsers (Chrome, Edge, Firefox, mobile browsers).
Design constraints: PHP and MySQL as required by the course; must run on low-cost hosting; no paid libraries.
Assumptions: the institution uses a CA/40 + Exam/60 split and a 4.0 grading scale (both configurable); each course has one lecturer per semester.

5. Architectural and Detailed Design

5.1 Software Architecture

SRMS uses a layered architecture organised as Model–View–Controller (MVC). Each layer talks only to the layer directly below it, which keeps business rules in one place and makes each layer testable on its own.

LayerResponsibilityComponents
PresentationReceive HTTP requests, check access, validate form input, render HTMLindex.php, Router, Controllers, Views
BusinessGrading rules, the approval workflow, GPA/CGPA calculationResultService, GradingScheme
Data accessAll SQL queries, transactions and the connectionRepositories, Database
DataPersistent storage with integrity constraintsMySQL 8 (SQLite for tests)

Why layered MVC instead of microservices: SRMS is a small system with one team and one database. Microservices would add network calls, deployment complexity and distributed data problems with no benefit at this scale. Layered MVC runs on cheap shared hosting and is easy for other PHP developers to maintain.

5.2 Design Patterns

PatternWhereJustification
MVCControllers / Views / ModelsSeparates page logic, HTML and data, so views can change without touching business rules.
Front Controllerpublic/index.php + RouterOne entry point means session start, error handling and the role check are written once and cannot be forgotten on a new page (supports NFR-03).
Repositorysrc/Models/*RepositoryAll SQL in one place; controllers and services work with arrays, not SQL. Tests can swap MySQL for an in-memory SQLite database.
SingletonDatabase::connection()One PDO connection per request instead of opening a new connection in every repository. setConnection() lets tests inject a test database.
StrategyGradingScheme interface, StandardGradingSchemeGrading scales differ between universities and change over time. A new scale is a new class passed to ResultService; no existing code changes (Open/Closed Principle).
Template MethodAbstract Controller and Repository base classesShared steps (render, redirect, CSRF check, prepared query) are defined once; subclasses only add their specific actions.
Dependency InjectionResultService constructorThe grading scheme and repositories are passed in (with defaults), which makes the service easy to test and extend.

5.3 Database Design

Entity–Relationship diagram

Normalisation

The schema is in Third Normal Form (3NF). Each table has a single-column primary key and all attributes depend only on that key. Students are separated from users so that login data is not repeated for each role. Enrolment is a separate associative entity that resolves the many-to-many relationship between students and courses. Results hang off enrolments, so a result cannot exist for a student who is not enrolled. total, grade and grade_point are stored, even though they are derived, as a deliberate denormalisation: they record the grade as awarded under the scale in force at the time, so a later change of grading scale cannot silently rewrite historical results.

6.3 Key Code

Grading strategy (BR-02)

final class StandardGradingScheme implements GradingScheme
{
    private const BANDS = [80 => ['A', 4.0], 75 => ['B+', 3.5], 70 => ['B', 3.0], 65 => ['C+', 2.5],
                           60 => ['C', 2.0], 55 => ['D+', 1.5], 50 => ['D', 1.0], 0 => ['F', 0.0]];

    public function grade(float $total): array
    {
        if ($total < 0 || $total > 100) {
            throw new ValidationException('Total score must be between 0 and 100.');
        }
        foreach (self::BANDS as $min => [$grade, $point]) {
            if ($total >= $min) return ['grade' => $grade, 'point' => $point];
        }
    }
}

Credit-weighted GPA (BR-03)

public static function gpa(array $courses): array
{
    $points = 0.0; $credits = 0;
    foreach ($courses as $c) {
        $points  += (float) $c['grade_point'] * (int) $c['credit_hours'];
        $credits += (int) $c['credit_hours'];
    }
    return [$credits > 0 ? round($points / $credits, 2) : 0.0, $points, $credits];
}

Submission rule (FR-10, BR-06)

public function submit(int $lecturerId, int $courseId): int
{
    $course  = $this->ownedCourse($lecturerId, $courseId);          // BR-05
    $summary = $this->results->statusSummary($courseId);
    if ($summary['missing'] > 0) {
        throw new ValidationException("{$summary['missing']} student(s) still have no score. ...");
    }
    $n = $this->results->changeStatusForCourse($courseId, 'draft', 'submitted', $lecturerId);
    $this->audit->log($lecturerId, 'results_submitted', "{$n} result(s) submitted for {$course['code']}");
    return $n;
}

9. Conclusion, Limitations and Future Work

9.1 Conclusion

The project delivered a working Student Result Management System that solves the problems in Section 1.2. Grades and GPAs are computed by one tested component. Results can only change through a controlled draft → submitted → published workflow with a full audit trail. Students see their own results privately as soon as they are approved. Every objective in Section 1.3 was met, and all 15 functional requirements trace to design elements and passing tests.

Applying the full SDLC showed the value of each phase. The written business rules (BR-01 to BR-07) became test cases directly. The state diagram defined the workflow that the code enforces. Exploratory testing found a high-severity usability defect (DEF-02) that scripted tests had missed.

9.2 Limitations

  • One lecturer per course; team-taught courses are not supported.
  • Scores are entered one class at a time; there is no spreadsheet import.
  • No password reset by email; the admin sets initial passwords.
  • The grading scale is set in code, not through an admin screen.

9.3 Future Work

  • Bulk upload of scores from Excel/CSV.
  • SMS or email notification when results are published.
  • Downloadable, digitally signed PDF transcripts.
  • Admin screen for grading scales and academic calendar.
  • Result analytics: pass rates and grade distribution per course.
  • Integration with the university student information system.
